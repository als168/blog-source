周六下午正想用 ChatGPT 查点东西，结果页面转半天没反应——如果你 11 月 21 日也遇到了，别怀疑自己的网，问题出在 OpenAI 那边。

当地时间 11 月 21 日下午 1 点 48 分到 5 点 21 分，ChatGPT 和 OpenAI API 大面积出错，整整 211 分钟，请求失败率一度冲到 75%。付费用户和免费用户一个没跑掉：登录登不上，对话加载不出来，文件传不上去，语音模式也哑了。开发者的 API 更惨，聊天补全、微调、图片、音频、实时接口，几乎全线报错。

OpenAI 当天就在状态页上发了完整的事故复盘，原因说出来有点让人哭笑不得：一次例行的数据库维护。

## 两个副本同时倒下，认证跟着全灭

出事的是 OpenAI 主 API 服务背后的一台 Postgres 数据库。更准确地说，是这台库的两个读副本。

这个主 API 服务管的是认证——全站的用户登录、服务之间的身份校验都要过它。维护期间，两个读副本同时挂了，而且挂得很有特点：不是直接断电，而是先失联、再越落越远，复制延迟一路涨到没边。副本本身是"承重"的，请求离不开它们，主库没事也救不了场。

OpenAI 的工程师试了好几轮：救活旧副本，失败；在别的区域拉起替代品，也失败。最后是拉上数据库服务商，在同一个区域起了两个新副本，才把服务抢回来。验证的方法也挺实在：把所有查询直接指向主库，确认故障假设成立，才算真正收尾。

## 这次复盘写得还算老实

比起很多厂商出事后发一句"我们深表歉意"，OpenAI 这份复盘的信息量算足的。整改清单列了四条：暂停同类维护，直到另行通知；调整数据库配置，减少连接抖动；上线一个功能开关，可以按比例把流量从副本上挪走；以后每次维护之前先做预审，恢复方案先备好再动手。

有意思的是时间点。11 月 21 日那个周五，纳斯达克 100 指数跌了 5.61%，创下六年来最差的一周。Anthropic 刚上市、AI 板块正被放在放大镜下看，一次 3.5 小时的宕机，难免被多读出几层意思。但就事论事，这次故障和模型能力没什么关系，纯粹是基础设施的运维翻车。

## 普通用户能从中学到什么

对每天离不开 ChatGPT 的人来说，这事的提醒很直接：别把所有鸡蛋放在一个篮子里。

如果你用 AI 赶工，本地留一份正在写的东西，关键对话定期导出一份；如果你的产品直接调 OpenAI 的 API，最好有个备用方案——哪怕只是降级提示和排队重试，而不是让用户对着报错干等。单点故障这东西，平时看不见，出一次就够呛。

至于 OpenAI 自己，复盘里承诺的那些措施管不管用，下次维护出问题的时候就知道了。基础设施的可靠性，从来不是靠一次复盘写出来的，是靠下一次不出事证明的。
