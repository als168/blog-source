每个程序员手里都有那么一两个老项目：跑得好好的，就是没文档。新人接手先花两天猜：这项目是干嘛的？怎么跑起来？配置从哪来？口口相传传着传着就变味了。让 AI 补一份 README 是个省事的办法，但直接一句「帮我写个 README」丢过去，出来的东西多半不能用——AI 没读过你的代码，只能凭空编。今天这篇讲一个靠谱的三步流程。

第一步，让 AI 先读代码，再动笔写。别急着要文档，先给 AI 交代清楚项目结构。你可以这样说：「这是我的项目，目录结构是这样的……入口文件是 main.py，配置文件在 config/ 目录下，数据库用 SQLite，依赖在 requirements.txt 里。先帮我梳理一下这个项目是干嘛的、模块之间怎么调用，不用写文档，先列个提纲给我确认。」这一步的关键是让 AI 先理解，再输出。项目大的话，分两次给：第一次给目录结构和入口文件，第二次给核心模块。一次塞几万行代码进去，AI 也抓不住重点。

第二步，给一份 README 大纲，让 AI 照着填。别让 AI 自由发挥结构，结构你来定，内容它来填。一份能直接用的 README，大纲一般是这几块：项目是干嘛的（一句话 + 解决什么问题）、快速开始（环境要求、安装命令、怎么跑起来）、配置说明（有哪些配置项、分别在哪改）、常用命令（开发、测试、部署各一条）、常见问题（跑不起来先看这里）。把大纲贴给 AI，让它按这个顺序写，每一块只写和你项目有关的内容，没有的就空着别编。

第三步，也是最重要的一步：逐段核对，别直接提交。AI 写文档最容易出问题的地方有三个：一是命令写错，比如把 pip install 写成 npm install；二是版本号对不上，文档里写的依赖版本和 requirements.txt 里的不一致；三是凭空编功能，项目里没有的接口，它看着像就给你写进去了。核对的办法很实在：文档里的每一条命令，自己在终端跑一遍；每一个版本号，对照 requirements.txt 或者 package.json 看一眼；每一个功能描述，回到代码里确认真的存在。跑不通的就改，改完再跑，直到按文档能从零跑起来为止。

顺手给一个能直接套用的提示词模板：

「请根据以下项目信息写一份 README：项目名是 X，用途是 Y，技术栈是 Z，入口文件是……，配置文件是……，依赖文件是……。README 结构按这个顺序：项目简介、快速开始、配置说明、常用命令、常见问题。只写代码里真实存在的内容，不确定的地方标注出来，不要编造。写完后列出你不确定的三个点，我来核对。」

最后那句「列出不确定的点」是我觉得最有用的地方。AI 自己标出来的不确定项，往往就是最容易错的地方，你核对的时候先看这三处，效率最高。

老项目补文档这件事，最难的不是写，是开始。按上面三步走，一个下午就能把最老的那个项目也补上，下次新人接手，至少不用再靠口口相传了。
